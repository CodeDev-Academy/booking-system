# Partner Handover Package — Clinic Booking System

**Phase 5 / Task 5.1.** This is the package we give the messaging partner (VoiceBip /
Meta WhatsApp) and the clinic's launch owner. It states what we provide, what the
partner must register, what the partner must give back, and how we jointly prove the
system end to end.

Everything here is **configuration only** — no code changes are needed on either side
to go from sandbox to live. The full flip procedure lives in
[`FLIP_LIVE_RUNBOOK.md`](./FLIP_LIVE_RUNBOOK.md); this package is the partner-facing
summary of the same system.

> Ground rule that never changes: **Django is the source of truth.** n8n orchestrates
> delivery but never holds database credentials. Provider keys live only in the n8n
> host's environment.

---

## 1. Who owns what

| Side | Owns |
|---|---|
| **Us (system)** | The Django backend (decides who is messaged and composes every message word), the n8n workflows (deliver only), the dashboards, all webhook URLs below, and the tokens marked *we generate* |
| **Partner (VoiceBip)** | Voice/ SMS sending: API key, registered caller ID, SMS sender ID, delivery-report + inbound-SMS webhooks on their side |
| **Partner (Meta)** | WhatsApp sending: phone number ID, permanent access token, approved message template, app subscription |
| **Clinic (launch owner)** | Clinic settings (name, phone, hours, services) via the dashboard; a test phone number they control |

## 2. Webhook URLs we provide (register these with the partner)

All URLs sit behind the public HTTPS n8n host (`https://<n8n-host>` — Railway or a
reverse proxy). `SERVER` below is that host.

| # | URL | Method | Registered with | Authentication | Purpose |
|---|---|---|---|---|---|
| 1 | `https://SERVER/webhook/provider-callback` | `POST` | **VoiceBip** dashboard (delivery reports / call outcomes) | Header **`X-Provider-Token: <PROVIDER_CALLBACK_TOKEN>`** (aliases accepted: `X-Callback-Token`, `X-Webhook-Token`) | Advances our message rows to `delivered` / `answered` / `no_answer` / `failed`, with the provider's own sentence on failures |
| 2 | `https://SERVER/webhook/provider-callback?token=<PROVIDER_CALLBACK_TOKEN>` | `GET` + `POST` | **Meta** app → WhatsApp → Configuration → Webhook | GET: the `hub.verify_token` handshake vs our `WHATSAPP_VERIFY_TOKEN` (echoes `hub.challenge`). POST: the URL token — only honoured because Meta cannot send custom headers (see the HMAC note in the runbook §5) | WhatsApp delivery statuses (batched `entry[]` envelopes understood natively) |
| 3 | `https://SERVER/webhook/sms-inbound` | `POST` | **VoiceBip** (only if they relay inbound SMS) | Header **`X-Webhook-Secret`** — confirm with VoiceBip that their inbound relay can set a custom header | Patient SMS replies ("1"/"2"/"3", "reschedule", "cancel") reach the reply handler |
| 4 | `https://SERVER/webhook/whatsapp-inbound` | `POST` | **Dormant at launch** — Meta-direct cannot use it (no handshake support, no custom headers, and Meta's own inbound messages arrive at URL 2 where they are acked `200 {"ok":true,"ignored":true,"reason":"inbound_message_not_a_status_event"}` on purpose). It exists for a BSP relay that *can* send `X-Webhook-Secret` | Header **`X-Webhook-Secret`** | Patient WhatsApp replies when such a relay is in place. **Telegram is the launch channel for interactive replies** |

Never registered with anyone (internal only):

| URL | Called by | Auth |
|---|---|---|
| `https://SERVER/webhook/dispatch-offers` | Django only, fire-and-forget | `X-Webhook-Secret` — a wrong or missing secret is refused `401` before anything is sent |
| `https://SERVER/webhook/intake` | The clinic's own booking page | none (public intake normalizer; Django re-validates everything) |
| `https://SERVER/webhook/provider-sim/*` | Dev-only simulator | deactivated and deleted before launch (runbook §6) |

## 3. Shared verification tokens

Three secrets, each with exactly one owner of the value and a two-sided rotation:

| Token | Generated by | Lives in | Shared with | Rotation rule |
|---|---|---|---|---|
| `DJANGO_WEBHOOK_SECRET` (Django side: `WEBHOOK_SECRET`) | **Us** | Django `.env` + `ClinicSetting.webhook_secret`; n8n env as `DJANGO_WEBHOOK_SECRET` | nobody outside the two of them | Change on **both** sides before restarting, or every dispatch/sweep/reply is refused `401` until they match again |
| `PROVIDER_CALLBACK_TOKEN` | **Us** (long, random) | n8n env; configured as the header in the VoiceBip dashboard; inside URL 2's query string for Meta | VoiceBip (header), Meta (URL — they keep it automatically) | Change in n8n env + restart + update the partner's configured header together. Treat as a production secret: a `?token=` appears in every execution log |
| `WHATSAPP_VERIFY_TOKEN` | **Us** (any string) | n8n env; typed into Meta's *Verify token* box at registration | Meta | Change in both places; Meta re-handshakes on the next save |

Django enforces the same discipline on every guarded endpoint (`X-Webhook-Secret`):
missing or wrong → **401 `{"error": "INVALID_WEBHOOK_SECRET"}`** and nothing is written.

## 5. What the partner must give back (Task 5.2)

- [ ] **VoiceBip**: API key + base URL; registered `+234` caller ID; SMS sender ID (default `Cedarcare`); voice agent id
- [ ] **VoiceBip**: delivery-report / call-outcome webhook — exact payload spec, and **can their dashboard set a custom header?** (decides URL 1 vs the `ALLOW_QUERY_TOKEN` escape hatch)
- [ ] **VoiceBip**: do they relay **inbound SMS** to a webhook, and with a custom header? (decides whether URL 3 goes live)
- [ ] **VoiceBip**: DND routing for free-text SMS on Nigerian numbers, or is a pre-registered template required (if so: template id + variable syntax)
- [ ] **Meta**: WhatsApp phone number ID + **permanent** access token
- [ ] **Meta**: approved utility-category template — name, language, and placeholder order must match `WHATSAPP_TEMPLATE_PARAM_ORDER` (default `patient_name,service_name,option_1,option_2,option_3,expiry`; quick replies optional via `WHATSAPP_TEMPLATE_QUICK_REPLIES`)

## 6. Joint acceptance run (Task 5.3)

Run the flip procedure in [`FLIP_LIVE_RUNBOOK.md`](./FLIP_LIVE_RUNBOOK.md) **together**,
in order: preconditions → env → mock regression gate → flip → SMS first, voice next,
WhatsApp last → register callbacks → smoke checklist (§7, all 14 items) → rollback
plan acknowledged. The full partner checklist (auth, customers CRUD, campaigns,
availability, appointments CRUD, interactions logging, campaign commands, realtime
updates, idempotency, retries, reconciliation, data isolation) is exercised in the same
session, ending with one complete patient journey end to end.

Failure handling the partner will see, by design: a held-back or failed send is a **row
with a plain-language reason** (Needs Attention tab / `queued` or `failed` interaction
rows), never a silent drop and never a crash — see the runbook's "Reading queued rows".

## 7. Internal notes (not part of the partner pack)

- Proven-live references: dispatch `05`, replies `04`, expiry sweeper `02`, reminders
  `03` — each with a node-only harness under `n8n/tests/` and a live proof recorded in
  `TEST.md` (T-708, T-713/T-713b, T-714/T-714b, T-715/T-715b).
- The reminder/reply/sweep webhooks all answer `401 {"error": "INVALID_WEBHOOK_SECRET"}`
  on a bad secret and are idempotent on `external_ref` (claim-ref upserts) — a partner
  retry can never duplicate a message row.
- If VoiceBip's payloads need vocabulary changes, the only edit points are
  `STATUS_ALIASES` / `CHANNEL_ALIASES` in `07`'s `Verify & Normalize Provider Event`
  (and the harness `n8n/tests/test_callback_auth.js` pins the auth contract around them).
